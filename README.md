# 會議逐字稿工具

把一段會議錄音變成一份可以逐句校正的逐字稿。全部在本機 CPU 執行，**音訊不會上傳到任何地方**。

```
錄音檔  →  分辨講者  →  切成一句一句  →  語音辨識  →  你逐句校正  →  匯出逐字稿
```

---

## 快速開始

### Windows（PowerShell）

```powershell
.\run.ps1
```

**就這一行。** 不用先安裝，也不用記第二個指令。

第一次執行會自己把環境準備好：找 Python（沒有就用 `winget` 裝）、建立 `.venv`、
裝套件、**偵測到 NVIDIA 顯示卡就順便把 GPU 加速裝起來**、下載約 220 MB 的模型，
然後啟動並打開瀏覽器。整個過程大約 3–5 分鐘，大部分時間在下載模型。

之後每次執行都只是啟動，幾秒鐘的事。中途斷掉也沒關係，再跑一次 `.\run.ps1`
會從沒做完的地方接下去，已經抓好的檔案不會重抓。

不想用 PowerShell 就直接**雙擊 `run.cmd`**，做的事情完全一樣。

### bash / WSL / macOS / Linux

```bash
./run.sh
```

一樣只有這一行，行為完全相同。

### 想自己控制安裝

平常用不到，需要時才用：

```powershell
.\run.ps1 -Setup      # 強制重跑一次安裝檢查
.\setup.ps1           # 只安裝不啟動
.\setup.ps1 -Cpu      # 安裝時完全不碰 GPU
.\setup.ps1 -Revert   # 已經裝了 GPU 版，換回 CPU 版
```

bash 版是 `./setup.sh`、`./setup.sh --cpu`、`./setup.sh --revert`。
兩邊抓的模型完全一樣，也都會核對檔案大小，下載到一半的檔案不會被當成正常的用。

## 怎麼用

1. **上傳錄音** — 按「＋ 新增會議」，可以**一次選多個檔案**。知道現場有幾個人就把「講者人數」選起來，分辨講者會準很多。
2. **不用等** — 上傳後專案立刻出現在左側清單，每個專案有自己的狀態與進度條，
   你可以同時排很多個、也可以先去編輯已經跑完的別的專案。
3. **標記講者** — 上方的講者列直接把「講者 1」改成 `Joseph`、「講者 2」改成 `Rebecca`。改一次，整份逐字稿都會跟著換。
4. **逐句校正** — 每一句右邊都有一個講者下拉選單。系統把 Joseph 的話聽成 Rebecca 時，就在那一句改回來，不會影響其他句子。
5. **匯出** — 「匯出逐字稿」可選純文字、Markdown、SRT/VTT 字幕、CSV、JSON。

### 校正時好用的功能

| 功能 | 位置 | 說明 |
|---|---|---|
| 改講者（單句） | 每句右側下拉選單 | 只改這一句 |
| 改講者（大量） | 「選取模式」→ 勾選多句 → 按講者按鈕 | 一次改一整段 |
| 改文字 | 直接點句子編輯 | 改過的句子底下會有虛線 |
| 重新辨識這句 | 🔁 | **一句裡有好幾個人講話時用**，見下方 |
| 切成兩句 | 游標放在要切的位置 → ✂ | 手動切，位置自己決定 |
| 合併 | ⭳ | 一句話被切太碎時用 |
| 播放該句 | 每句左邊的 ▶ | **只播這一句，播完就停**；校對講者時最好用，播放中會變成 ⏸，再按一次停 |
| 從這裡接著播 | 點左邊的時間 | 從這句開始一直往下播 |
| 整理逐字稿 | 上方「整理逐字稿」 | 依目前的詞語修正、標點與斷句規則重整一次，不用重跑辨識。有東西可整理時按鈕會顯示數量 |
| 播放器 | 浮在專案畫面底部 | 逐字稿再長也一直看得到；切換專案會跟著換 |
| 鍵盤 | 空白鍵播放/暫停、←→ 快轉 3 秒（+Shift 為 10 秒） | |

改過講者的句子，下拉選單會變成橘色框，方便你回頭檢查改了哪些。

## 辨識模型

預設是 **X-ASR Zipformer 中英**，安裝時就一併裝好，不用另外下載。

會選它是實測的結果，不是偏好：拿一場 69 分鐘的中英混說研討會，用同一批時間區間讓每個模型
重跑一次，數 13 個上下文可以確定講過的技術名詞：

| 模型 | 認出幾個 | 備註 |
|---|---|---|
| **X-ASR Zipformer**（預設） | **9 / 13** | 176 MB，速度也最快 |
| FireRedASR2 | 9 / 13 | 英文全部大寫，1.2 GB |
| Cohere Transcribe | 7 / 13 | 唯一唸對 Discovery Phase |
| Qwen3-ASR | 6 / 13 | 有一句完全沒輸出 |
| SenseVoice | 5 / 13 | 英文常糊掉：phage display 變成 `f display`、candidate 變成 `can` |

其餘模型按右上角「模型設定」下載，之後永久可用。SenseVoice 仍在清單裡，需要日／韓／粵時再抓。

排名、WER 與下載數是**執行時直接向 Hugging Face 取得的**，不是寫死在程式裡：

- **排名／WER／RTFx** — [Open ASR Leaderboard](https://huggingface.co/spaces/hf-audio/open_asr_leaderboard)
- **下載數／讚數／授權／更新時間** — Hugging Face Hub API

模型設定頁最上方會標明資料來源與抓取時間，並有「立即更新」按鈕。快取 12 小時，離線時
沿用上次的資料；完全沒有資料時就不顯示排名，而不是猜。

**注意**：Open ASR Leaderboard 只評測**英文短音檔**。清單裡的中文模型（SenseVoice、
FireRedASR2、Paraformer、X-ASR）不在該榜上，會標示「未列入」——這是事實陳述，不代表它們
中文表現差。中文情境請自己用實際錄音比較。

### 語言設定

部分模型需要指定辨識語言：**Cohere Transcribe 沒有指定語言就會整份輸出空白**。
新增會議時若選到這類模型，會出現「辨識語言」欄位（預設中文）。其餘模型沒有這個欄位。

若某次辨識所有片段都沒有文字，工具會直接判定為失敗並說明原因，而不是存下一份空的逐字稿。

### 重新辨識

**整份重跑** — 專案上方的「重新辨識」。換模型、換講者人數、換語言後從頭跑一次。
目前的逐字稿、講者名字和所有手動修改**都會被清除**（按下去前會再確認一次），音檔保留。
就算原始上傳檔已經清掉也能重跑，因為用的是專案裡那份 16 kHz 的 `audio.wav`。

**只重跑一句**（🔁）— 適用「這一句其實是三個人在講，但被併成一句了」。
指定人數後，工具只對那一段音訊重新做講者分離與辨識，然後把原本那一句**換成拆出來的數句**。

拆出來的句子會用**聲紋**比對回專案裡既有的講者，不會憑空多出「講者 4」：

- 從每位講者已經說過的話建立聲紋（會排除正在重跑的那一句，避免它為自己背書）
- 相似度門檻 0.60。實測同一人約 0.88、不同人約 0.33，門檻落在中間留有餘裕
- 比對不到既有講者才會新增，並提示你去確認名字
- **如果重跑後仍然只有一個人**，講者維持原樣，不會因為分數勉強就被改掉
- 每一句都會顯示比對分數，方便你判斷是否可信

## 同時處理多個會議

上傳不會卡住畫面：專案會**立刻建立**並排進佇列，每個專案自己顯示
**排隊中（前面還有 N 個）／辨識中 xx%／完成／失敗**，還有剩餘時間估計。

- 想排幾個就排幾個，一次選多個檔案也行。
- 同時執行的數量由 CPU 核心數決定（見下方），其餘排隊等待。
- 任何一個都可以單獨**取消**；失敗的可以單獨**重新辨識**。
- 一個專案失敗不會影響其他專案。
- 辨識中也能去編輯另一個已經跑完的專案。

### 執行緒不是越多越好（實測）

「每個專案幾個執行緒」控制的是 **ONNX 在單一句子內部的平行度**，不是同時處理幾個句子。
會議的句子都很短，這種平行化很快就吃不滿：

| 設定 | 60 句耗時 |
|---|---|
| 6 執行緒 | 13.8 秒 |
| 20 執行緒 | 17.1 秒 |

**20 執行緒比 6 慢。** 想更快的正確做法是**同時多跑幾個專案**，不是把單一專案的執行緒開大。
選超過建議值時，介面會直接提示。

句子是**分批**送進辨識器的（`decode_streams`，預設一批 16 句）。實測比一句一句解碼快
約 1.8 倍，輸出文字完全相同。批次大小可用 `SCRIBE_BATCH` 調整。

### GPU 加速（NVIDIA）

**不用自己動手。** 只要機器上有 NVIDIA 顯示卡，第一次跑 `.\run.ps1` 就會一併裝好：

1. GPU 版 sherpa-onnx（約 200 MB）
2. CUDA 12 執行環境 + cuDNN 9 的 pip 版（約 600 MB）

**不需要安裝 3 GB 的 CUDA Toolkit** —— NVIDIA 的 pip 套件就帶了需要的 DLL。

**裝不起來也不會讓安裝失敗**：沒有顯示卡、驅動沒裝、CUDA 起不來，都只是退回
CPU 繼續跑完。功能完全一樣，只有辨識那一段慢一點。

#### 筆電的獨顯可以隨時開關

很多筆電（Optimus／MUX）可以把獨顯關掉，所以**「現在能不能用」和「這台機器有沒有
顯示卡」是兩回事**。工具是這樣處理的：

- **安裝時**只看硬體在不在。卡在、但現在被關著，一樣把 GPU 版套件裝好。
- **用哪個裝置是每次啟動重新實測的**，不是裝好就定死。所以你把獨顯切回來之後，
  直接再跑 `.\run.ps1` 就會用到 GPU，**不用重裝、也不用改設定**。

啟動時主控台會寫明這一次用的是什麼。

### 混合架構：每個階段各用最快的裝置

實測（RTX 3070 Ti Laptop，5 分鐘錄音）發現 GPU 並非全面較快：

| 階段 | CPU | GPU | 採用 |
|---|---|---|---|
| 語音辨識 | 12.6 秒 | **0.9 秒** | **GPU**（快 14 倍） |
| 講者分離 | **55.3 秒** | 91.7 秒 | **CPU**（GPU 慢 1.7 倍） |
| **整體** | 60.7 秒 | 92 秒 | **混合 44.8 秒** |

**為什麼講者分離用 GPU 反而慢？** 不是因為片段短，而是因為**每次輸入長度都不一樣**。
拿同一批 62 段做實驗：

| 每次輸入的長度 | CPU | GPU |
|---|---|---|
| 全部一樣長 | 3.76 秒 | **0.88 秒**（GPU 快 4.3 倍）|
| 5 種長度輪流 | 4.36 秒 | 8.21 秒（GPU 慢 1.9 倍）|
| 每次都不同 | 3.00 秒 | 8.28 秒（GPU 慢 2.8 倍）|

ONNX Runtime 的 CUDA 後端每遇到新的輸入形狀就要重新規劃執行計畫（cuDNN 還會為每個
形狀重新搜尋最佳卷積演算法）。講者分離每次送進去的語音片段長度都不同，等於每一次
呼叫都在付這筆錢——**只要 5 種長度輪流就足以把 GPU 的優勢吃光**。

**切句子（VAD）放 GPU 也慢，但原因不一樣。** 它的輸入形狀是固定的（每次 512 取樣），
可是每次只算 32 毫秒的音訊、模型只有 640 KB——啟動 GPU 核心和來回搬資料的成本，
遠大於運算本身。5 分鐘音檔要呼叫約 9,400 次：CPU 3.76 秒，GPU **37.19 秒**。

所以 GPU 輸的方式有兩種：**形狀一直變**，或**每次工作量太小**。
語音辨識兩個都避開了——大模型、整批送、長度補齊成一致，所以贏 14 倍。

### 每個階段各用什麼

| 階段 | 裝置 | 原因（皆為實測） |
|---|---|---|
| 讀取音檔 | CPU | 不是神經網路，是音訊解碼 |
| 分辨講者 | CPU | GPU 慢 1.9 倍——每次輸入長度都不同 |
| 切句子 | CPU | GPU 慢 10 倍——每次只算 32 毫秒 |
| **語音辨識** | **GPU** | **GPU 快 14 倍**——大模型、整批、形狀一致 |
| 聲紋比對 | CPU | 同分辨講者，片段長度不一 |

**預設就是這個組合，不需要手動設定。**

想改變預設：

```powershell
$env:SCRIBE_PROVIDER = "cpu"             # 全部用 CPU
$env:SCRIBE_DIARIZE_PROVIDER = "cuda"    # 講者分離也用 GPU（實測較慢）
```

啟動時主控台會寫明目前用什麼：

```
運算裝置：CUDA　使用 GPU：NVIDIA GeForce RTX 3070 Ti Laptop GPU（8 GB）
```

**偵測是實測而非猜測。** 光是裝了 GPU 版套件不代表能用——還要 CUDA 執行環境到位。
工具會實際載入一個模型試跑，確定 CUDA 真的起來才回報 GPU，否則明確告訴你缺什麼並
自動退回 CPU。

### 記憶體

**工具不管記憶體，交給作業系統的虛擬記憶體處理。** 閒置的模型會被分頁到分頁檔，
之後不再讀取，成本是磁碟空間而不是速度。實測（32 GB 機器、49 GB SSD 分頁檔、
兩個大工作同時跑）：分頁速率 16 pages/sec、磁碟 3 MB/s，瓶頸完全在 CPU。

所以辨識工作**不會因為記憶體看起來不足就被擋下**，載入過的模型也不會被主動釋放。
真的需要設上限（例如關掉分頁檔的機器）才用 `$env:SCRIBE_MODEL_RAM_MB = "4096"`。

### 多專案同時跑，硬體吃得滿嗎

實測（20 核 + RTX 3070 Ti，3 分鐘錄音）：

| 情況 | 耗時 | CPU 使用率 | GPU 使用率 |
|---|---|---|---|
| 單一專案 | 37.9 秒 | 33.7% | 5.5% |
| 三個並行 | 61.0 秒（每個平均 20.3 秒）| **88.4%** | 5.2% |

**單一專案只用得到約 1/3 的 CPU**，因為講者分離最多只吃 6 條執行緒（實測開更多反而變慢）。
要用滿機器，靠的是**同時跑多個專案**，不是把單一專案的執行緒開大。

丟 4 個專案、改變同時執行數的吞吐量：

| 同時執行 | 每個執行緒 | 總耗時 | 吞吐 |
|---|---|---|---|
| 1 | 6 | 104.0 秒 | 6.9× |
| 2 | 6 | **78.0 秒** | **9.2×** |
| 3 | 6 | 82.1 秒 | 8.8×（預設）|
| 4 | 6 | 81.3 秒 | 8.9× |
| 2 | 10 | 128.9 秒 | 5.6× |

2～4 個並行差距在 5% 以內，預設的 3 沒問題；但**只跑一個會少掉三成吞吐**。

**GPU 使用率只有 5% 是正常的**，不是浪費。語音辨識加速 14 倍之後只剩全程約 2% 的時間，
剩下的講者分離因為輸入形狀一直變（見上），放 GPU 反而更慢。

### CPU 用多少

兩個設定相乘就是實際吃掉的核心數，啟動時會依你的 CPU 自動決定：

| | 說明 |
|---|---|
| 同時處理幾個專案 | `CPU 核心數 ÷ 每專案執行緒數`，上限 8 |
| 每個專案幾個執行緒 | 預設 `(核心數 - 2) ÷ 3`，上限 6 |

例如 **20 核心** → 同時 **3 個專案 × 每個 6 執行緒 = 18 核心**，留 2 核給系統。
這是**真正的並行**，不是輪流跑；第 4 個之後才排隊。

想自己指定就設環境變數：

```powershell
$env:SCRIBE_JOBS = 4      # 同時處理 4 個專案
$env:SCRIBE_THREADS = 4   # 每個用 4 執行緒
.\run.ps1
```

同一個模型只會載入**一份**並由所有專案共用，所以同時跑 3 個不會吃 3 倍記憶體。

## 支援的音訊格式

`m4a`、`mp3`、`wav`、`flac`、`mp4`、`mov`、`wma`、`opus`、`webm`、`aac`、`alac`、`amr`、`ogg`、`3gp` …

wav / flac / ogg 由 libsndfile 直接讀取，其餘交給 PyAV（內含 FFmpeg 函式庫）處理，
**不需要另外安裝 ffmpeg 執行檔**。所有音訊都會先轉成 16 kHz 單聲道，這是模型要求的格式。

## 命令列用法

不開網頁也能用：

```powershell
.\run.ps1 models                                   # 列出所有模型
.\run.ps1 pull x-asr-zipformer-punct               # 下載模型
.\run.ps1 run meeting.m4a -s 2 -o transcript.txt   # 直接產生逐字稿
.\run.ps1 run meeting.m4a -m fire-red-asr2-ctc -f srt -o subs.srt
.\run.ps1 -Port 8000                               # 換連接埠
```

`run` 的參數：`-s` 講者人數（-1 為自動）、`-m` 模型、`-f` 格式（txt/md/srt/vtt/csv/json）、
`-o` 輸出檔、`-t` 執行緒數、`--zh` 中文轉換（`s2twp` 簡轉繁台灣用詞 / `none` 不轉換）。

```
    ├── test_e2e.py             完整流程（需要音訊合成，會佔用顯示卡）
    ├── test_queue.py           辨識佇列
    ├── test_downloads.py       下載佇列
    ├── test_rework.py          重新辨識與聲紋
    ├── test_memory.py          記憶體查詢
    ├── test_textfixes.py       標點、詞語修正與斷句
    └── test_tidy.py            舊逐字稿套用目前的文字修正
```

每個會議資料夾是自足的，整包複製到別台電腦也能用。
**備份只要複製 `data/`** —— 模型隨時可以重新下載，`data/` 才是刪掉就沒有的東西。

### 刪除會議

兩個地方都可以刪：左側清單每一列滑過去會出現 🗑，或是打開專案後按右上角的「刪除」。

**逐字稿和音檔會一起刪掉，而且沒有垃圾桶、救不回來**，所以按下去前一定會再問一次。
正在辨識中的專案也可以直接刪，工作會先被取消。

## 運作原理

講者分離與語音辨識是**分開跑**再交叉的：

1. **pyannote segmentation + 3D-Speaker 聲紋** 算出「誰在什麼時候說話」。
2. **Silero VAD** 算出「哪裡有聲音」，切出一句一句。
3. 兩者交集 — 一個 VAD 語音塊如果中間換人講話，就在換人的時間點切開，
   而不是整塊算給講最久的人。這是逐句都能正確歸屬的關鍵。
4. 每一小段送進 ASR 辨識。
5. 同一人連續且間隔 < 1.2 秒的句子，在畫面上合併成一個對話框，但底層仍是獨立的句子，
   所以你可以只改其中一句的講者。

## 疑難排解

**分不出講者 / 全部算成同一人**
上傳時把「講者人數」明確選起來，比自動偵測可靠得多。
若兩人聲音相近（例如同性別），這是聲紋模型的先天限制，用「選取模式」批次修正會比較快。

**辨識很慢**
換小模型（X-ASR Zipformer 176 MB）、把執行緒調高，或先把錄音剪掉開頭寒暄的部分。

**辨識出簡體字**
上傳時「中文轉換」選「簡轉繁（台灣用詞）」。已經跑完的專案，模型會保留原文，
未手動編輯過的句子會在切換時一併重新轉換。

**某些格式讀不進來**
先確認副檔名有在支援清單裡。少數冷門編碼可能還是需要外部 ffmpeg，
此時把檔案轉成 wav 或 mp3 即可。

**辨識時介面卡住、無法新增專案或切換**
這個已經修好了。原因是講者分離的原生程式會鎖住 Python 直譯器，一次可達 8～11 秒，
期間伺服器無法回應任何請求。現在講者分離改在獨立子行程執行，實測最慢回應從 8.5 秒
降到 0.03 秒。任何請求進行中，畫面頂端都會有一條進度條，切換專案時也會顯示載入中。

**專案一直顯示「辨識中」不動**
如果伺服器中途重開過，舊的工作就不存在了。工具啟動時會自動把這種專案標成
**「已中斷」**，按「重新辨識」即可。若狀態確實在跑，伺服器視窗會逐階段印出進度與耗時。

**想複製錯誤訊息**
錯誤視窗上有「複製錯誤訊息」按鈕。同一份內容也會印在兩個地方：

- **伺服器視窗**（跑 `run.ps1` 的那個終端機）—— 含完整 Python traceback
- **瀏覽器主控台** —— 按 F12 → Console

**模型顯示「不完整」**
上次下載被中斷了。到「模型設定」按「補齊下載」即可，已下載的檔案不會重抓。
啟動時工具也會自動清掉中斷留下的 `.part` 暫存檔。

## 測試

```powershell
.venv\Scripts\python.exe tests\test_e2e.py
```

會用 Windows 內建語音合成產生一段雙人對話，跑完整條流程 —— 上傳、辨識、講者改名、
逐句改講者、切句、合併、批次指定、六種格式匯出、錯誤處理，最後清理乾淨。
它會自己開一個伺服器，所以**不要和其他會載入模型的程式同時跑**，會搶同一張顯示卡的記憶體。

其餘五個測試不需要音檔，幾秒鐘就跑完：

```powershell
.venv\Scripts\python.exe tests\test_queue.py       # 辨識佇列、並行名額、取消
.venv\Scripts\python.exe tests\test_downloads.py   # 下載佇列、續傳、檔案完整性
.venv\Scripts\python.exe tests\test_rework.py      # 重新辨識、聲紋比對
.venv\Scripts\python.exe tests\test_memory.py      # 記憶體查詢與模型上限
.venv\Scripts\python.exe tests\test_textfixes.py   # 長度上限、附加元件擋關、標點、斷句
.venv\Scripts\python.exe tests\test_tidy.py        # 舊逐字稿套用目前的文字修正
```

每個檔案都是獨立的腳本，直接執行即可，沒有測試框架。
